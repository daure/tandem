Why Stop can look like failure: Docker sends a stop signal, then may force-kill after a timeout. Exit 143 or 137 can accompany an intentional stop. Neither proves a crash; 137 alone does not prove an out-of-memory kill.

Setup jobs: Waiting → Running → ✓ Completed (exit 0) or × Failed (non-zero). A confirmed stop of an unfinished job means ■ Interrupted. Show active/failed/interrupted jobs; collapse completed jobs.

3. Show the action while it is happening

◌ Creating / Starting / Restarting / Stopping / Deleting belongs to the operation’s target. A service restart leaves siblings unchanged; the parent can say “Restarting db · 2/3 running.” Keep observed problems visible alongside activity.

Remove activity when the operation ends; report “Stop failed” without overwriting runtime truth. Deletion stays visible until containers and owned-resource cleanup finish; retain “Cleanup failed” when resources remain.

4. Keep the visual language literal

■ Gray · inactive▶ Blue · active/unverified✓ Green · verified success! Amber · attention/uncertainty× Red · confirmed problem

Color the status glyph and label; keep names neutral. Use ■ for stopped, Ⅱ for paused, and a spinner only for actual activity. Keep the globe beside the URL—it denotes a route, not health. Use tuicore semantic colors and ASCII fallbacks.

Scope matters: templates are Valid / Invalid / Missing, with instance counts. Gateway availability is shared infrastructure. A route URL is configuration; “last readiness check passed” needs a timestamp. Healthy never promises browser reachability.

Implementation guardrails & evidence
  1. One service-owned projection: retain typed Docker state, health, exit code, OOM flag, error, identity and timestamps. TUI and MCP consume the same classification; action availability uses lifecycle capabilities, not resource consumption.
  2. Stop provenance: persist target container IDs + start generation before stopping, then confirm per-target results. Share across TUI/MCP processes; supersede on a new run. An attempted stop cannot excuse an earlier crash or hide OOM evidence. Unknown external intent stays unknown.
  3. Expected topology: retain the rendered launch service/replica set and setup roles. Compare against fresh Docker inventory; template edits do not silently redefine an existing instance. While creating, not-yet-created targets are Waiting. A failed create without containers remains an operation result, not a running inventory row.
  4. Bound activity: associate it with a live operation/lease and deadline, including across processes. A lost worker becomes “Operation interrupted; refresh required.” Docker health and route-readiness results stay separate; route checks run during startup/restart, so retain their time and run identity.
  5. Actions: Start for stopped/created containers; Stop for running/restarting targets; paused targets need Unpause before Start/Restart. Missing/dead containers require recreation. Keep details available during stale observations, and revalidate ownership/state before mutations.
  6. Resource colors: memory pressure is separate from health. Retain cap-based warnings; mark old samples stale and show “—” for unavailable data.

Code evidence

docker.rs:144–155 merges exited/dead into down (exit N); rows.rs:61–115 promotes non-zero exits to Failed and paused to Stopped. resources.rs:220–308 explicitly expects Failed for 137/143.

rows.rs:462–506 filters setup jobs from the tree and omits child status labels. environments/mod.rs holds process-local operations and preserves snapshots on inspection failure. lifecycle.rs:205–215 reports stop success from the Docker command result.

Acceptance checks: requested stop with 0/137/143; unexplained 137; explicit OOM; mixed stopped/running; paused; failed setup; dead/missing container; health recovery; restart transient; stale Docker; failed cleanup; reconnect after stop.
