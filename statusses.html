Why Stop can look like failure: Docker sends a stop signal, then may force-kill after a timeout. Exit 143 or 137 can accompany an intentional stop. Neither proves a crash; 137 alone does not prove an out-of-memory kill.

3. Show the action while it is happening

⠋ Creating / Starting / Restarting / Stopping / Deleting belongs to the operation’s target. A service restart leaves siblings unchanged; the parent can say “Restarting db · 2/3 running.” Keep observed problems visible alongside activity.

End activity on success, failure or worker loss. “Stop failed · cannot confirm outcome” leaves runtime Stale. Keep deletion visible through owned-resource cleanup; if containers are gone but cleanup fails, retain an operation/cleanup row rather than inventing a live instance.

4. Resources follow lifecycle—not row visibility

TUI cadence: inspect every 10s terminal-focused / 5min unfocused; sample when 60s is due, after inspection. Focus gain requests inspection immediately; sample if due/newly eligible. Collapse, filtering, offscreen rows and panel focus do not change sampling.

SituationMemory / CPU display
Creating / instance start activeMuted “—” for that instance and its children; excluded from sampling. On completion—even failure—sample any surviving eligible containers.
Running / checking / unhealthyShow readings. Health does not gate usage. Keep previous readings during refresh; memory arrives first, CPU after a valid second reading.
PausedShow sampled memory; CPU “— · paused.” Paused memory still contributes to totals.
Not started / stopped / restarting / removing / dead / missingMuted “—”; clear live readings for those targets. Unaffected siblings keep theirs. While stopping but still running, retain measured usage.
Sampling failure / stale inventoryDim last-known readings with age and “stale”; otherwise “—.” A resource error does not change lifecycle or health.

Manual refresh: force eligible targets; successful baselines trigger a second reading after a 1s pause, and completion waits for sampling. New runs/eligibility changes get targeted samples without shifting everyone else’s 60s deadline.

Keep memory above CPU and reserve the column width. “—” means unavailable/inapplicable; measured zero is 0. Totals include collapsed/filtered children and running setup jobs when eligible; label startup exclusions or incomplete coverage “partial.”

Resource freshness, totals & safeguards
  1. Freshness: show sample age in details. Mark stale on failure or age over 120s focused / 600s unfocused; use the focused policy without focus reporting. Clear errors only after that container/metric succeeds. Inventory and metric freshness are separate; template errors permit sampling, Docker inspection errors block it.
  2. Identity & timing: key samples by container ID and start generation. Reject late results after replacement/restart/stop. Reset CPU baselines on a new run or pause/resume; show “—” until two valid readings. CPU is an interval average and may exceed 100%; memory is Docker working set. Readings have a 10s budget, at most eight requests in parallel.
  3. Coverage: memory sums running + paused containers; CPU sums running containers. Compute each metric independently. If an eligible contributor lacks a reading, show “— · partial,” not an understated sum; stale contributors make the total stale. Empty contributor sets show “—.” Startup exclusions carry a partial badge even when a subtotal is available.
  4. Presentation: fresh memory is amber at 70% and red at 90% of explicit caps; aggregate pressure needs complete fresh coverage and caps for every contributor. CPU and uncapped memory stay neutral. Stale values are muted with an amber qualifier. Sampling indicators belong to Refresh/metrics, not the lifecycle spinner.
  5. Scheduling: coalesce work; never overlap samples. A manual request during sampling queues a forced follow-up rather than disappearing. One failed container preserves other readings. MCP returns its process-local cached metrics with freshness, possibly unavailable; each list call does not start a polling loop.

5. Keep the visual language literal

 Gray · inactive Blue · active/unverified Green · verified success Amber · attention/uncertainty Red · confirmed problem

Color the status glyph and label; keep names neutral and issue qualifiers independently colored. Use JetBrainsMono Nerd Font and tuicore::Spinner for activity, respecting animation settings; ⠋ is a static preview. Docker recovery uses amber , explicit restart uses the blue spinner.

Structure:  Template ·  Instance ·  Service ·  Setup ·  Route (beside URL). State glyphs take the tree’s leading slot; type icons belong in details. Valid/Succeeded use ; Invalid uses . Semantic theme colors and readable labels remain authoritative without icons.

Scope matters: templates are Valid / Invalid / Missing, with instance counts. Gateway availability is shared infrastructure. A route URL is configuration; “last readiness check passed” needs a timestamp. Healthy never promises browser reachability.

Implementation guardrails & evidence
  1. One service-owned projection: retain typed Docker state, health, exit code, OOM flag, error, identity and timestamps. TUI and MCP consume the same classification; action availability uses lifecycle capabilities, not resource consumption.
  2. Stop provenance: under the instance lock, inspect first and persist target IDs, start generations and request time before stopping. Record each confirmed result; a partial stop only explains matching targets. Share across TUI/MCP, supersede on a new run, and retain earlier crashes/OOM evidence. A raced job exit 0 needs evidence of interruption before losing Completed status.
  3. Expected topology: retain the launch service/replica set for selected profiles, plus setup roles. Compare by container identity and replica slot; count only expected long-running slots. Template edits do not redefine an existing instance. During creation, not-yet-created targets are Waiting; after failure they are Missing. Unknown topology prevents an “all healthy” claim.
  4. Setup-only rollup: unknown/stale first, retaining known failures as qualifiers. Otherwise Failed if any job failed, then Interrupted if any interrupted, then Degraded for missing/dead/unhealthy jobs. All completed means Completed; remaining jobs are Running if any run, Paused if unfinished jobs are all paused, Waiting if all await start, otherwise Degraded.
  5. Bound activity: associate it with a live operation/lease and deadline, including across processes. A lost worker becomes “Operation interrupted; refresh required.” Startup metric suppression ends with that lease. Start/restart success requires the targeted run to satisfy configured health and route checks; retain route-check time and run identity separately from Docker health.
  6. Actions: Start for stopped/created containers; Stop for running/restarting targets; paused targets need Unpause before Start/Restart. Missing/dead containers require recreation. Keep details available while stale, and revalidate ownership/state before mutations. Metrics never enable or disable lifecycle actions.
